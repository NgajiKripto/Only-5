# Comprehensive security hardening for autonomous crypto agent

This change addresses ten security audit findings across the codebase of an autonomous Solana trading bot: SSRF protection via DNS resolution, shared-secret inter-service authentication, transaction safety verification, expanded prompt injection detection (base64, homoglyphs, LLM control tokens, indirect injection), an async mutex for financial operations, timing-safe passphrase comparison with rate limiting, Zod schema validation for LLM-generated JSON, pinned npm dependency versions, and database file permission enforcement. The approach is defense-in-depth hardening at the application layer, keeping each mitigation self-contained and backward-compatible.

Watch for: SSRF validator is vulnerable to DNS rebinding / TOCTOU since it resolves the hostname then hands control to a separate fetch call (confirmed). The rate limiter in TelegramBot has no cleanup mechanism and will leak memory over time for distinct chat IDs (confirmed). The rate limiter also permanently soft-blocks any chat ID that once triggered the limit because the counter never resets after the block window expires (confirmed). The `healthCheck` and `listAgents` endpoints in service clients omit the Authorization header, creating an inconsistent auth posture (confirmed). No dedicated unit tests exist for the URL validator, the async mutex, or the new prompt-guard rules (confirmed).

## High-level view

The SSRF protection resolves hostnames via DNS before allowing outbound requests, catching direct IP literals and private-range resolved addresses. The resolution is decoupled from the actual HTTP fetch, so a DNS result can change between check and use (classic TOCTOU). The mitigation covers the common case but is not watertight against a determined attacker with DNS control.

Inter-service auth attaches a Bearer token from `INTERNAL_SERVICE_SECRET` to all mutating HTTP requests in the three service clients. Read-only endpoints (`healthCheck`, `listAgents`) skip the header, which means the services must implement per-route auth decisions or these endpoints are unprotected. The secret travels in plain text over HTTP since the service URLs default to `http://localhost:*`.

The prompt-guard expansion adds three new regex rules, Cyrillic homoglyph normalization, expanded leet-speak tables, and recursive base64 decoding with re-analysis. The base64 candidate regex (`[A-Za-z0-9+/=]{20,}`) will fire on many non-base64 strings in normal text (SHA hashes, Solana addresses, UUIDs), inflating scores on benign inputs.

Timing-safe passphrase comparison and rate limiting in the Telegram bot close the original timing-oracle and brute-force gaps. The rate-limit state lives in an in-memory Map that never evicts entries and never resets the failure counter after a block window expires, creating both a slow memory leak and a permanent-soft-block bug.

## SSRF protection via DNS-based URL validation

The TOCTOU gap is the primary concern: `validateUrlNotInternal` resolves the hostname and verifies the IP, then returns. The caller subsequently calls `fetch(url)`, which performs its own DNS resolution. Between the two lookups, an attacker with control of the DNS server can return a different (private) IP. Fixing it requires either a custom `fetch` agent that connects to the pre-resolved IP (pinning), or a `connect` event hook that checks the socket's `remoteAddress` and aborts if private.

Additionally, the function silently passes when DNS lookup fails (catch block at line 63-66 logs debug and returns without throwing). An unresolvable hostname passes validation and the fetch attempt will fail later with a connection error — not a security hole, but the SSRF guard provides no signal to the caller about lookup failures versus legitimate passes.

```
┌─────────────────┐         ┌───────────────┐          ┌─────────────────┐
│ Caller          │         │ validateUrl   │          │ fetch()         │
│ (scanner/cmd)   │────────▶│ NotInternal() │────────▶ │ (new DNS query) │
└─────────────────┘         └───────────────┘          └─────────────────┘
                              DNS query #1                DNS query #2
                              (may differ)                (attacker rebinds)
```

## Prompt injection base64 false-positive risk

The base64 recursive analysis scans the normalized input for sequences of 20+ base64-alphabet characters, attempts to decode each, checks if the result is printable ASCII of 10+ characters, then re-runs all rules against the decoded content. The regex `[A-Za-z0-9+/=]{20,}` matches any 20-character alphanumeric run, including SHA-256 hashes, base58 Solana addresses, UUIDs without dashes, and long English words. If decoded junk happens to match a rule pattern, it inflates the score and may push benign input into the "review" or "block" tier.

A tighter check would verify valid base64 padding (`=` at end, length divisible by 4) before attempting decode, or raise the threshold to 40+ characters.

## Timing-safe auth: rate limiter permanent-block bug

Rate limiting blocks a chat ID for 15 minutes after 5 failed attempts. The counter is not reset after the block expires. If a user hits 5 failures, gets blocked for 15 minutes, then comes back:

1. `attempts.blockedUntil > Date.now()` is false (block expired) — passes the check.
2. `attempts.count` is still >= 5.
3. The next single failure calls `trackFailedAttempt`, which increments count to 6, and since `count >= MAX_AUTH_ATTEMPTS` is still true, sets a new `blockedUntil`.

This creates a permanent-soft-block for any chat ID that once triggered the limiter. Fix by resetting `count` to 0 when `blockedUntil` has passed.

The `failedAttempts` Map also grows without bound — add a periodic sweep or size cap to evict expired entries.

## Inter-service authentication gaps

`healthCheck()` in executor and orchestrator clients, and `listAgents()` in orchestrator, do not call `getHeaders()`. If the receiving services enforce auth on all routes, health checks will fail when the secret is configured. If services only enforce auth on mutating routes, the design works but creates confusion about which endpoints are protected.

The token is transmitted over HTTP by default (service URLs are `http://localhost:*`). This is secure for same-host deployment but becomes a credential leak if services are split across hosts without a TLS reverse proxy.

## Test coverage gaps

- `src/core/url-validator.ts` — zero tests. The 172.16-31 range check, IPv6 handling, and DNS error path are never exercised.
- `src/core/mutex.ts` — zero tests. Lock ordering, error propagation through `withLock`, and concurrent contention are untested.
- New prompt-guard rules (LLM tokens, indirect injection, encoding exfiltration), homoglyph normalization, and base64 recursive analysis — zero tests.
- Rate limiting logic in TelegramBot — zero tests. Existing tests verify passphrase success but not blocking after failures.
- `verifyTransactionSafety` — not directly tested.
