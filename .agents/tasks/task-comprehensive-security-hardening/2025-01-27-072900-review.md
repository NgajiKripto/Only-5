# Comprehensive security hardening for autonomous crypto agent (v2)

This change addresses ten security audit findings across an autonomous Solana trading bot: SSRF protection, inter-service auth, transaction verification, expanded prompt injection detection, an async mutex, timing-safe passphrase comparison with rate limiting, Zod validation of LLM output, pinned deps, DB file permissions, and internal network guard config. The v2 iteration fixes the rate-limiter permanent-block bug, adds auth headers to all service client endpoints, tightens the base64 regex to reduce false positives, and adds dedicated test suites for the URL validator, mutex, and prompt-guard rules.

Watch for: `verifyTransactionSafety` logs warnings for suspicious transactions but does not reject them, meaning it provides observability without enforcement (confirmed). The rate-limiter cleanup is lazy (per-chatId on next access), so entries from chat IDs that never retry still accumulate without bound (likely). The SSRF TOCTOU gap and service secret over HTTP remain architectural constraints acknowledged from v1.

**Verdict**: APPROVED

## High-level view

The rate-limiter permanent-block bug is fixed: expired entries are deleted on next access, which also serves as lazy eviction. There is no periodic sweep, so entries from chat IDs that trigger the block and never come back accumulate indefinitely. Given that the passphrase is single-use (`passphraseUsed = true` after first successful auth), the realistic growth is bounded to the number of distinct attackers during a single bot lifetime.

The base64 regex in prompt-guard is tightened to `[A-Za-z0-9+/]{40,}={0,2}` with a padding-alignment check (`length % 4 === 0`). Solana addresses (44 chars, base58 alphabet overlapping base64) may still trigger decode attempts on occasion — the printable-ASCII heuristic provides a second gate that prevents score inflation from gibberish decodes.

Transaction safety verification calls `verifyTransactionSafety` before signing but never throws. A malicious transaction constructed to drain funds through an unknown program will still be signed and submitted while a warning sits in the log file.

## Transaction verification as a monitoring-only gate

`verifyTransactionSafety` is called in `signAndSendVersionedTransaction` before signing. Both checks (instruction count and unknown program IDs) produce `logger.warn` calls and nothing else — the method returns void and never throws.

```typescript
private verifyTransactionSafety(transaction: VersionedTransaction, opts?: { maxInstructions?: number }): void {
  // ...
  if (instructions.length > maxInstructions) {
    logger.warn("Transaction has unusually high instruction count", { count, max });
  }
  // ...
  if (programId && !KNOWN_PROGRAM_IDS.has(programId)) {
    logger.warn("Transaction references unknown program", { programId });
  }
}
```

For a crypto agent managing real funds, a warning that nobody is watching in real-time provides limited protection. The known-program allowlist is narrow (System, Token, Associated Token, Jupiter v6, Compute Budget) — but without enforcement, an attacker who can manipulate the upstream swap response could inject instructions to an arbitrary program. The transaction would be signed and submitted.

Adding a `strict` option that throws for unknown programs (with a caller opt-out for explicitly new integrations) would convert this from monitoring to enforcement without breaking backward compatibility.

## Rate-limiter eviction gap

Entries from chat IDs that are never revisited remain in the map permanently. If an attacker rotates through thousands of distinct chat IDs to probe passphrases, each that hits 5 failures leaves a ~50-byte entry. In practice, the single-use passphrase makes sustained brute-force from multiple IDs pointless — once any ID succeeds, all further attempts fail. The unbounded growth scenario requires an attacker who knows the passphrase is already consumed and keeps hammering anyway, which yields no benefit.

## Test coverage gaps

Not tested: the rate-limiting logic in TelegramBot (block-after-5, expiry, lazy eviction) has no dedicated test. `verifyTransactionSafety` is also untested directly — the warning logic for unknown programs and high instruction counts is not asserted anywhere.
