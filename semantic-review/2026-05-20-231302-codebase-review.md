# Only-5: Autonomous Money-Making Agent — Full Codebase Review

An autonomous Solana-based agent that evaluates and executes money-making strategies (on-chain arbitrage, airdrop farming, GitHub bounties, content creation, microtasks) via LLM-guided decision-making. It runs a 30-second evaluation loop, persists decisions in SQLite, enforces risk limits, and exposes a Telegram interface for monitoring and control.

**Watch for:** Private key exposed in memory with no access boundary (confirmed). Telegram auth can be bypassed by anyone who observes the startup log (confirmed). The on-chain strategy executes only the forward leg of an arbitrage, not the round-trip — so the "arbitrage" framing is misleading and will reliably lose to slippage (confirmed). Risk manager tracks `openPositions` but nothing ever calls `openPosition()`/`closePosition()`, so the exposure check is permanently bypassed (confirmed). Three of five strategies (bounty, content, microtask) are no-ops that burn LLM tokens without producing revenue (confirmed).

## High-level view

The core loop is architecturally clean: scheduler fires `evaluateStrategies` every 30 seconds, strategies return scored opportunities, the agent uses LLM to rank them, risk manager gates execution, outcomes are recorded, and the learning system periodically extracts patterns. The separation between scheduling, strategy evaluation, risk gating, and execution is well-defined and testable.

Security posture is the primary weakness. The Solana private key is decoded at module load and stored as a `Keypair` object in a class that exposes `getKeypair()` publicly. Telegram authorization relies on a passphrase printed to stdout at startup — any process with log access can impersonate the owner. There is no encryption-at-rest, no key rotation, and no HSM/KMS integration.

The on-chain strategy claims to perform arbitrage but only executes a single swap (A→B), not a round-trip (A→B→A). The evaluation checks round-trip profitability to decide whether to trade, but execution only does one leg. This will lose money to fees and slippage on every execution since there's no mechanism to convert back.

The risk manager is well-designed in theory (daily loss caps, position sizing, cooldown after loss, minimum balance protection) but has a gap: `openPositions` is never incremented during actual trade execution, so the max-exposure check always sees zero open exposure and passes unconditionally.

The non-trading strategies (bounty, content, microtask) generate LLM responses and store them in memory but never submit work to any platform. They return `profitLoss: 0` and `success: true`, polluting the learning system's success-rate metrics with false positives.

<summary>Issues (9)</summary>

1. **Private key unrestricted access** — `WalletManager.getKeypair()` exposes the raw private key to any code that holds a reference. Restrict signing to an internal method; never expose the `Keypair` object.
2. **Telegram auth passphrase in stdout** — The generated one-time passphrase is logged to console, readable by any co-tenant or log aggregation service. Store it in a secure channel or require out-of-band delivery.
3. **Passphrase single-use without expiry** — Once used, `passphraseUsed = true` prevents re-auth, but a leaked passphrase grants permanent access since authorized chat IDs are never persisted or revocable without restart.
4. **Arbitrage executes one leg only** — `OnchainStrategy.execute()` performs a single A→B swap despite the evaluate step checking A→B→A profitability. Either execute both legs or rename the strategy to directional swap.
5. **openPosition/closePosition never called** — The risk manager's exposure tracking is dead code; `canTrade()` always sees `openPositions = 0`, so the max-exposure guard never fires.
6. **No-op strategies inflate success metrics** — Bounty, content, and microtask strategies return `success: true` without producing revenue, skewing the learning system's pattern analysis.
7. **Unbounded observations table** — `memory.remember()` appends to `observations` with no TTL or pruning. On a 30-second evaluation loop calling multiple strategies, this table grows without bound.
8. **No transaction timeout/retry on swap execution** — `signAndSendSwap` has a 30-second confirmation poll but no retry or fallback if the transaction is dropped by the network.
9. **Log file read via Telegram** — `/logs` and `/errors` commands read the full log file into memory with no size cap before slicing, risking OOM on large files.

## Private key handling and wallet security

The `WalletManager` decodes the base58 private key at construction and stores it as a `Keypair`. The class then exposes three public methods (`getKeypair()`, `getConnection()`, `signTransaction()`) that give any caller full signing authority. In `jupiter.ts`, `signAndSendSwap` receives the raw keypair directly:

```typescript
const signature = await signAndSendSwap(
  swapTx,
  this.wallet.getKeypair(),  // raw Keypair exposed
  this.wallet.getConnection()
);
```

A safer pattern would encapsulate signing inside `WalletManager` so the private key never leaves the object boundary. The current design means any strategy (including future third-party strategies) that receives a `WalletManager` reference can sign arbitrary transactions.

The banner in `index.ts` prints the last 8 characters of `SOLANA_PRIVATE_KEY` to the log. While partial, this leaks information about key material to log aggregation systems.

## Telegram authorization model

Authorization follows a two-path scheme: either a pre-configured `TELEGRAM_OWNER_CHAT_ID` or a one-time passphrase. When neither env var is set, the system generates a UUID passphrase and prints it to stdout. This is the only delivery channel — anyone with access to the process log (Docker logs, PM2 logs, systemd journal) can read it.

The passphrase is single-use (`passphraseUsed` flag), which prevents replay, but authorized chat IDs are stored only in memory. A restart wipes authorization, requiring a new passphrase. There's no mechanism to revoke a specific chat ID without restarting the process.

The authorization middleware runs on every update, but commands are registered after it in `setupTelegram()`. This ordering is correct (middleware executes before command handlers in Grammy's pipeline). However, the middleware unconditionally calls `next()` after successful passphrase auth, which means the passphrase message itself gets routed to command handlers — no issue in practice since it won't match any command, but it's a subtle ordering dependency.

## On-chain strategy: single-leg execution

The evaluation logic correctly models round-trip arbitrage (get quote A→B, then quote B→A, check if `endAmount > startAmount`). But `execute()` only performs the forward swap:

```typescript
const quote = await getQuote(pair.inputMint, pair.outputMint, tradeAmount, this.slippageBps);
const swapTx = await executeSwap(quote, this.wallet.publicKey.toBase58());
const signature = await signAndSendSwap(swapTx, ...);
```

There is no second swap back to the original token. The strategy then measures P&L by comparing SOL balance before and after — but if the swap was SOL→USDC, the SOL balance will always decrease (by the swap amount plus fees). The actual "profit" from arbitrage only materializes if you close the loop. As implemented, this will record a loss on every successful execution.

Additionally, the `tradeAmount` calculation uses `balance * 0.1` for SOL pairs, passing this as the `expectedReward` field to the risk manager's `canTrade()`. But `expectedReward` is the potential profit, not the trade size — the risk check is gating against the wrong value.

## Risk manager: exposure tracking gap

The `RiskManager` maintains an `openPositions` field and checks it in `canTrade()`:

```typescript
const totalExposure = this.openPositions + amount;
if (totalExposure > maxExposureAmount) { ... }
```

But neither `AgentController.executeOpportunity()` nor any strategy implementation calls `riskManager.openPosition(amount)` before execution or `riskManager.closePosition(amount)` after. The field stays at zero (or whatever was restored from persisted state), so this check never triggers. This is a design-level gap — either remove the exposure concept or integrate it into the execution flow.

## No-op strategies and metrics pollution

Three strategies — `BountyStrategy`, `ContentStrategy`, and `MicrotaskStrategy` — follow the same pattern: evaluate using LLM, generate a response, store it in memory, return `{ success: true, profitLoss: 0 }`. None submit work anywhere. Each has a TODO comment acknowledging this.

The problem is that the learning system treats `success: true` outcomes as positive signals when computing strategy performance. The `extractPatterns()` method counts outcomes by the decision record's `outcome` field, which the agent sets to `"success"` for these strategies. This inflates their apparent success rate, potentially causing the LLM ranking step to prefer them over strategies that actually produce revenue.

## Database growth and memory unbounded accumulation

Every evaluation cycle that finds an opportunity records a decision. With 30-second cycles and multiple strategies, this can produce 2,800+ records per day. The `observations` table additionally stores every `remember()` call — risk state, P&L, trades, content, interactions, learning insights. There is no vacuum, no TTL, no archival.

The risk manager's `persistState()` stores up to 100 trades in a single JSON blob per call, creating a new observation row each time. Over time this creates substantial duplication (the full trade list is stored on every state change).

The `recall()` method's `LIMIT` clause bounds query results but not table size. A deployment running for months will accumulate a large SQLite file with no mechanism for cleanup.

## Jupiter integration and transaction confirmation

The `signAndSendSwap` function polls `getSignatureStatus` every second for up to 30 seconds. If the transaction is dropped (network congestion, expired blockhash), it simply returns `false`. The caller (strategy) then reports `success: false` but has already consumed gas for the submission attempt. There's no retry with a fresh blockhash.

The `maxRetries: 2` parameter in `sendRawTransaction` handles RPC-level retries but not blockhash expiration. Jupiter quotes have a `lastValidBlockHeight` that isn't checked against current block height before submission.

## Log file reading in Telegram commands

The `/logs` command reads the entire `logs/agent.log` file into memory:

```typescript
const content = readFileSync(LOG_FILE, "utf-8");
const allLines = content.trim().split("\n").filter((l) => l.length > 0);
return allLines.slice(-count);
```

On a long-running agent producing structured JSON logs every 30 seconds, this file can grow to hundreds of MB. Reading it synchronously blocks the event loop and risks OOM. A tail-based approach (reading from the end of the file) or log rotation would be more appropriate.

## Learning system reliability

The learning system sends all recent decisions as JSON to the LLM and expects a specific JSON format back. The parsing is defensive (regex extraction of JSON, field validation), which is good. But the system stores every LLM "insight" as a new skill with a timestamped name (`insight_${strategy}_${Date.now()}`), which means the skills table grows without bound — one entry per insight per learning cycle.

The confidence score system (`updateConfidence`) uses in-memory state only (not persisted to the DB). A restart resets all strategy confidence to 0.5, losing learned preferences.

## Test coverage gaps

The test suite covers the core modules well (memory, risk, wallet, strategies, telegram commands, agent lifecycle). Notable gaps:

- No test for the actual `evaluateStrategies → executeOpportunity` end-to-end flow with multiple competing strategies and LLM ranking.
- No test for the authorization middleware's interaction with command handlers (the middleware is tested in isolation, commands are tested in isolation, but the composition in `setupTelegram` is not).
- No test for `signAndSendSwap` (the Jupiter integration's most critical function).
- No test for the learning system's `runLearningCycle` with realistic LLM responses.
- The content and microtask strategies have no dedicated tests.
